# Architecture (draft v0)

_This is a proposal to be ratified via ADRs in milestone M0. Wire protocols and local security follow [ADR-003](adr/003-wire-protocols.md) (accepted 2026-11-09). Language and runtime follow [ADR-002](adr/002-language-runtime.md) (accepted 2026-11-09): TypeScript on Node 24 or later, no Bun. The build-vs-extend choice is [ADR-001](adr/001-build-vs-extend.md) (accepted 2026-11-09, option C: standalone with interop)._

## 1. Roles

```
                         ┌──────────────────────────────┐
   You  ◄──────────────► │          CONDUCTOR           │  frontier model, high effort
 (web UI / TUI /         │  global daemon on localhost   │
  phone / Slack…)        │  • decision inbox             │
                         │  • cross-project workflows    │
                         │  • global config & profiles   │
                         │  • cost ledger, registry      │
                         └──────┬───────────┬───────────┘
                    JSON-RPC/WS │           │ (A2A-shaped tasks)
              ┌─────────────────▼──┐     ┌──▼─────────────────┐
              │  MINI-CONDUCTOR    │     │  MINI-CONDUCTOR    │  mid-tier model
              │  repo: api-service │     │  repo: research/   │
              │  • task queue      │     │  …                 │
              │  • worker pool     │     └────────────────────┘
              │  • escalation gate │
              │  • handoff manager │
              │  • MCP server      │
              └──┬───────┬──────┬──┘
     adapters    │       │      │
          ┌──────▼─┐ ┌───▼──┐ ┌─▼──────┐
          │ Claude │ │Codex │ │ Gemini │   cheap / low-effort workers
          │  Code  │ │      │ │  (ACP) │   each in its own git worktree
          └────────┘ └──────┘ └────────┘
```

The Conductor listens on one local port and mini-conductors dial in over JSON-RPC/WebSocket, so there is one port and no per-repo port discovery. A mini-conductor that runs standalone serves the same methods on its own port for the CLI and UI ([ADR-003 §4](adr/003-wire-protocols.md#4-conductor--mini-conductor-a2a-shapes-over-a-json-rpc-websocket)).

**Standalone today (M1, #21).** Until that port exists, `tacet run "<task>"` hosts the Mini-conductor in its own process until the task is done (`@tacet/mini/standalone`), answering escalations at the terminal or through `tacet run --resume --answer <id>=<text>`. `tacet status`, `tacet logs` and `tacet attach` read the repo's event log read-only from another process and never write to it, so the log keeps one writer, under the Mini-conductor's lock. Workers' checkouts are detached git worktrees under the repo's state directory, made by the worktree manager (#16, §2.4); the planner's throwaway checkout is force-removed after planning. `attach` follows a Worker session through the log; live terminal attach needs the port (#201). `tacet cancel <task>` (#202) cancels a task and its unfinished sub-tasks while no run is live: it takes the Mini-conductor's lock, ends Worker processes a crashed run left behind (#127), and records `worker.ended` (`canceled`) and `task.status canceled`, so `tacet run --resume` leaves the task alone. During a run, interrupt it first; in-process, `MiniConductor.cancel()` also ends the open sessions, discards their vendor resume state and stops the task's planner. Checkouts are left for the worktree manager (#210, #211), and the resume state of sessions stopped earlier for a restart is kept until its retention ends. Claude Workers cannot edit yet: every approval but the Mini-conductor's own tools is refused until a policy exists (#200, #25).

| Role | Lives | Owns | Talks to |
|---|---|---|---|
| **Conductor** | One per machine, `tacet up` | User attention, cross-repo plans, global policy, registry of mini-conductors, aggregated cost | User (UI/channels), mini-conductors |
| **Mini-conductor** | One per repo/workspace, installed via package, config in `.tacet/` | Task decomposition within the repo, worker lifecycle, worktrees, verification, escalation filtering, handoffs | Conductor (up), workers (down, via adapters + MCP) |
| **Worker** (sub-agent) | Short-lived agent sessions | One task or sub-task | Mini-conductor only (MCP tools + adapter events) |

A mini-conductor can run **without** a Conductor (standalone mode) — useful on its own, and makes adoption incremental.

## 2. Core loops

### 2.1 Task flow
1. User (or a workflow) gives the Conductor a goal; Conductor routes it to one or more mini-conductors as **tasks** (A2A-shaped: id, goal, acceptance criteria, budget, priority).
2. Mini-conductor plans → sub-tasks → picks adapter+model per its tier policy → spawns workers in worktrees.
   - The plan is one `task.planned` event (`TaskPlan`: sub-tasks with `dependsOn`), written in the same batch as one `task.created` per sub-task with `parentId`. Each `task.planned` is the full current plan: a replan lists every sub-task again, completed ones included. A sub-task's own `task.created` is authoritative for its goal and criteria. A sub-task kind a receiver does not know reads as `explore`, the read-only kind (owner decision, 2026-11-09). Dependencies live in the plan, not on `Task`, because `Task.parentId` is A2A `referenceTaskIds` and sub-tasks stay internal to the Mini-conductor ([ADR-003 §4](adr/003-wire-protocols.md#4-conductor--mini-conductor-a2a-shapes-over-a-json-rpc-websocket)).
   - A sub-task is scheduled once every sub-task it depends on is `completed`, within the `workers` capacity limits (§4).
3. Workers report via events and MCP tools; mini-conductor verifies (tests, lint, reviewer agent).
   - A Worker turn that ends idle with no pending escalation or approval is *finished*, not completed: it goes through verification first. One that ends with an escalation pending with the user is `input_required`. The parent task mirrors `input_required` (and `auth_required`) while a sub-task waits.
   - An escalation answer reaches the Worker that asked as its next message, sent only between turns and recorded as `escalation.delivered` once sent. An answer the gate gives in time comes back in the tool result itself and is recorded as delivered (`inline`). An answer that arrives while no session is open (after a restart or a failed run) goes into the first message of the next session.
   - The Worker pool is the Mini-conductor daemon in `@tacet/mini` (`MiniConductor`, #17). It runs one instance per repo (a lock file), Workers only on the API-key route, and answers a Worker's approval requests by an interim policy until policies exist (#25; owner decision on #200, 2026-11-10): the exact names of its own MCP tools are allowed; Claude Code's file tools (`Read`, `Write`, `Edit`, `NotebookEdit`, `Glob`, `Grep`, from `claude-sdk`, `acp:claude-acp` or `pty:claude`) are allowed when every target resolves inside the Worker's own checkout (`decideToolRequest`, decided afresh for each request: no surrounding whitespace or control characters (Claude Code trims a path before resolving it), no `..` or backslash, no leading `$` or `%`, no name NTFS or a URL-aware tool may read as another (a trailing dot or space, a colon, an 8.3 short name), no absolute path elsewhere, no symlink out or dangling, no `.git` as a case-insensitive file system may read it (case-folded after NFKC, with the code points HFS+ ignores removed, and NTFS's `git~1`), no write to a file with other hard links, no input key the tool's verified input does not have, no input the adapter redacted (the tool runs on the original), for Glob patterns no braces, no wildcard segment that could match `.git` other than a bare `*` or `**` (so a listing can show `.git` names, never contents), and a literal directory inside the checkout, resolved from the tool's own `path`; Grep's `glob` is refused (Claude Code splits it and passes each piece after its own `!.git` exclude); no write to agent, hook or tool config at any depth, names folded the same way: `.claude/`, `.cursor/`, `.gemini/`, `.codex/`, `.husky/`, `.github/workflows/`, `.tacet/` (Tacet's own config, #227), `.vscode/{tasks,launch,settings}.json`, `.vscode/mcp.json`, `.mcp.json`, `.envrc`, `.npmrc`, `.yarnrc*`, `.pre-commit-config.yaml`, `lefthook.yml`, which the user's own tools, or Tacet's next run, would load once the branch is merged; checked on the path as written and after symlinks; a symlink in a protected name at the checkout's root (at any of its components) or inside a protected directory there (at any depth, through linked directories) protects what it points at too, even before that exists, compared with names folded; a link loop, a link to the checkout root, or protected directories of over 2000 entries refuse every write in the checkout (deeper protected names only by their own name); a task that needs one escalates. The list cannot be complete: build files such as `package.json` scripts or a `Makefile` also run code, and stay writable because they are the work itself); everything else is refused: Bash and any shell, web tools, other MCP servers, unknown tools, and every other adapter's requests. A refusal is a summary-grade `worker.approval` event, kept and forwarded; an allowed request is a transcript-grade `agent.approval.decision` with the same payload, dropped by retention (owner decision on #200). The reason never holds a path outside the checkout. The checks fail closed: some ordinary names are refused too (`backup~1.txt`, `a:b.txt`, `10:30.log`, `notes.`), and a Worker that needs one escalates. Only names inside the checkout are judged, never the checkout's own parent directories. Paths are checked when the request is decided, not when the tool runs; that is safe only while a Worker cannot make a symlink or hard link in between (no shell, no link-making tool), so it must be revisited before any such tool is allowed. Calls a vendor does not ask about are closed off at the source (#206): an unattended Claude SDK Worker gets only the file tools (`tools`), with Bash, PowerShell and Monitor removed (`disallowedTools`), and a `PreToolUse` hook (failing closed) that asks Tacet about `Read`, `Glob` and `Grep`, which the SDK otherwise runs without `canUseTool` inside its working directory; the planner's own session may read and search inside its throwaway checkout by the same policy. A Claude Worker over ACP (`acp:claude-acp`) gets the same six file tools and no shell through `_meta.claudeCode.options`, with an inline `settings` ask rule for `Read`, `Glob` and `Grep`: ask rules come before a tool's own approval of a read in its working directory, so every read and search reaches `canUseTool` and so `session/request_permission`, which the policy decides (#214). Both routes take prompts verbatim (`verbatimPrompts`): text a Worker wrote reaches its next prompt (a `verify` command's output, review findings), and an `@path` there would otherwise be read into the prompt unasked, outside the checkout too (#214 review). A custom ACP preset that runs claude-agent-acp (by its bin, its npm package or the old `@zed-industries/claude-code-acp`, or a path into its package) is refused for Workers (`use acp:claude-acp`), since it would get none of that; a wrapper script that hides the command is not caught. For `pty:claude`, its `PreToolUse` hook already asks about every tool, so Bash is refused per call, and it has no `Glob` or `Grep`; whether interactive Claude Code expands an `@path` in a typed prompt without asking is not yet verified (#226) (the SDK and ACP settings verified live against the bundled Claude Code and claude-agent-acp 0.101.0 with the mock Messages API; capability matrix §1). `completed` keeps its A2A meaning, "done and verified", and its `task.result` has `verification.status: passed`, except where verification was not run (no `verify` commands configured to run, no verifier, or a Codex Worker until the owner's decision, #19), which `verification.status: not_run` says.
   - Verification (#19): after integration, the repo's `verify` commands run on the Worker's checkout (`CommandVerifier`, `@tacet/mini`) as Worker code: `/bin/sh -c`, the Worker environment allowlist (no vendor keys, §6), `CI=true`, stdin closed, its own process group, a per-command timeout (`workers.verify_timeout_s`, default 600), in order, stopping at the first failure. The checkout must be a linked worktree of the repo (never the main checkout or the shared `.git` as cwd) and exactly the integrated commit, before and after the commands: no tracked changes, no untracked files that are not ignored, no index entries marked assume-unchanged or skip-worktree (git runs with hooks off, no submodule recursion, as for integration). Ignored files, such as installed dependencies, stay and take part in the run. So `completed` means the integrated commit passed, together with whatever ignored files the checkout holds. Each command's result is a summary-grade `worker.verification` event (round, command, status, exit code, duration, commit; never output). A failure goes back to the same session as its next turn, with a redacted tail of the output (8 KB), up to `workers.verify_fix_attempts` times (default 2); then the attempt fails as before (`task.result` failed, a fresh session within `max_attempts`): the fix rounds and `max_attempts` are the escalation ladder before `FAILED` (ADR-003). A session that ends while it is verified (a restart, a stop) ends the run as `not_run`, not as a failed attempt. Commands come only from the effective config, never from the Worker's checkout; a command ends when its shell exits, and whatever it left running (in its process group or not) carries a fresh marker and is ended then (#127). A fresh attempt after a failed verification is told why (the redacted `notes`); a restart in the middle of a fix keeps the fix-round budget. Codex Workers are not verified yet (`VERIFY_CODEX_WORKERS`, recorded as `not_run`, "codex verify pending sandbox decision"), pending the owner's decision in §6; the switch matches the built-in adapter ids `codex-app-server` and `acp:codex-acp` only, not a custom `acp:` or `pty:` preset that runs Codex. Without a verifier (the entry point builds one with `commandVerifierFromConfig`, which takes the Worker environment allowlist and `verify_timeout_s` from config), `verify` commands are recorded as `not_run`, and such a sub-task still completes with `verification.status: not_run`, as Codex Workers' do.
   - Review (#19, off by default: `review.enabled`): after the `verify` commands pass (or are `not_run`, as for Codex Workers), a reviewer agent on `tiers.review` judges the integrated change (`AdapterReviewer`, `@tacet/mini`). It is the Mini-conductor's own session, like the planner's: on the API-key route, with no Tacet MCP server (no token, no Worker tools), every approval request refused, and its working directory an empty temporary directory of its own, never a checkout (a vendor CLI loads project settings, hooks and instructions from its working directory: the Claude Agent SDK loads every settings source unless told otherwise), with a process marker of its own (#127). The Mini-conductor gives it the change in the prompt: `git diff` from the checkout's base to the integrated commit, read in the main repo from integrated objects with hooks, external diff drivers, textconv and user-wide attributes off, redacted and then cut to 64 KB, with the `--stat` kept whole, between markers the change cannot guess. A checkout that started at the main branch records no base, so the diff starts where the commit left the main checkout's HEAD; if HEAD already holds the commit (the user checked out or merged its branch), the review gives no verdict rather than an empty change. The verdict is strict JSON read only from the reviewer's own reply (`approve`, or `request_changes` with at least one blocker or major finding; an invalid reply is retried once), so nothing in the Worker's checkout can approve it. Blocking findings go back to the same session as its next turn (redacted, at most 8 KB, framed as another agent's view to check), sharing the fix-round budget with the commands: a round is one check of a commit, commands and review together, so a repo without `verify` commands still has a cap on reviews. A reviewer that gives no verdict (an error, a timeout) leaves the work `partial`, never `passed` (pending the owner: block instead); a review stopped by a restart or a stop records no verdict and uses no fix round. The verdict is a summary-grade `worker.review` event (round, adapter, model, status, counts by severity, duration, commit; never the findings' text) and `verification.review` in `task.result`, whose `notes` carry the counts too; commands `not_run` with an approving review is `partial`. The reviewer's usage is charged to the sub-task. Every turn that integrated a commit is reviewed, whatever the sub-task's kind (the planner chooses kinds); one that integrated none is not. The task layer may turn review on, and may not change `tiers.review` or declare any tier's `vendor`. With `tiers.review.cross_vendor` (default true) the reviewer must run a different vendor's models than `tiers.worker` (Omnigent's Polly pattern, ADR-001): built-in adapters are known (`vendorOf` in `@tacet/core`), and OpenCode or a custom agent needs `tiers.<name>.vendor`; a reviewer of the same or an unknown vendor, a `pty:` reviewer (its tools cannot be refused) or a Codex reviewer (`REVIEW_WITH_CODEX`, until it is verified that Codex runs nothing without asking) is a startup error. Planner `review` sub-tasks are another use of `tiers.review`: they are Workers, not this gate.
   - A new checkout starts from the work of the sub-tasks it depends on, directly or through others (#134; a review that commits nothing passes its dependencies' work on): the commit of a single dependency, or a merge of several made in the main repo without a checkout (`git merge-tree --write-tree`, so git 2.38 or later, and `commit-tree`, authored by the Mini-conductor), recorded as `baseCommit` in `worker.started`. When their work conflicts, the user is asked first and nothing runs; once answered, the sub-task starts from the first dependency's work and its Worker is told to merge the rest, again on every retry along with the answer. A git error while combining is retried on later ticks, up to `max_attempts`. When a task completes, the work of all its sub-tasks is combined the same way into `tacet/<task>/result` (git cannot have `tacet/<task>` next to the sub-task branches `tacet/<task>/<n>`); if independent sub-tasks conflict there, nothing is combined and the task's result says so in its open questions.
   - Worker health (#17): each session has a heartbeat, fed by every adapter event and every `report_progress`. A Worker silent in the middle of a turn for `workers.stuck_after_s` gets `worker.nudged` (recorded only: the Claude and Codex adapters queue input sent during a turn as the next turn, so a hung Worker would never read a message); still silent `workers.nudge_grace_s` later, its session ends as `stuck` and a replacement session starts (`previousSessionId`), within `max_attempts`. A session between turns (waiting on an answer) is never judged stuck, nor one inside a tool call until the call has been open for `stuck_after_s + nudge_grace_s`. The heartbeat starts afresh when a turn starts and when a Mini-conductor restarts. A Worker that keeps reporting progress or calling tools without getting anywhere is not caught by this; that needs a separate limit.
4. Results roll up as **summary packets**, never transcripts: each verified (sub-)task gets a `task.result` (`SummaryPacket`), which goes up to the Conductor as an A2A Artifact with media type `application/vnd.tacet.summary+json`.

### 2.2 Escalation flow
- Workers call MCP `escalate({question, options?, urgency, contextRef?})`. The call does not block on a human: if the gate does not resolve it within a few seconds, it returns `pending`, and the answer arrives as the worker's next message ([ADR-003 §6](adr/003-wire-protocols.md#6-workers--mini-conductor-mcp-tool-surface)). Adapters can also surface a permission or approval request.
- Mini-conductor's **escalation gate** first tries to resolve it: repo policy, past decisions log, its own reasoning. Only unresolved items go up.
- Conductor dedupes/batches across repos and puts them in the **decision inbox**, ranked by urgency × blocked-workers.
- User answers once; the answer is recorded as a **decision** (reusable precedent) and flows back down.
- Escalation strictness is a per-user/per-repo dial (`autonomy: low | medium | high`).

### 2.3 Handoff flow
- Context usage tracked per session; at the `handoff` band the worker is asked for a typed **HandoffPacket** (see RESEARCH.md §5).
- Packet validated → stored in `.tacet/handoffs/<task>/<n>.json` → session closed → new session seeded with it (model may change per policy).
- The same packet type is used for mini→conductor summaries and for the Conductor's own self-handoff.

### 2.4 Worker worktrees
- The Mini-conductor creates each Worker at a detached HEAD in a dedicated worktree outside the repository. `WorktreeManager` implements the daemon's `Workspaces` port. A checkout starts at a full commit id or a local branch (default: the checked-out branch); unattended Workers write new objects only to their private per-worktree object store.
- Git maintenance of Worker worktrees uses the manager-owned Git directory explicitly, disables fsmonitor, hooks, reflogs, replace refs, and background maintenance; detached HEAD Workers remain tracked by their worktree path. Rebase is not exposed until it can update refs without reading Worker-controlled admin state.
- Setup commands are opt-in, run with argv rather than shell interpolation, have a timeout, and receive a limited environment by default. Tacet does not copy `.env` files.
- Removal never loses work unless forced (`remove(id, { force: true })`), and garbage collection only removes stale worktrees that pass the same checks. A worktree is kept while it has local, untracked or ignored files; while its HEAD, its HEAD reflog or its `tacet/<worktree-id>` branch holds a commit that no branch outside `tacet/*`, tag or remote-tracking ref contains (another `tacet/*` branch never counts: it is removable too, and two concurrent removals could each rely on the other's); and while its private object store holds a commit the shared store lacks. For Workers without a sandbox, which write the shared store, this is best effort: a commit they leave behind by moving HEAD is found only through the HEAD reflog, so it is lost if git did not write one (`core.logAllRefUpdates=false`) or the Worker expired it. Private objects are enumerated as files, never by handing the Worker's object store to git. A private store with packs, one that cannot be fully read, or a named commit that cannot be found keeps the worktree. Commits a Worker abandoned (by an amend or a reset) can never be integrated, so such worktrees are freed only by `force`. Work merged by squash or rebase elsewhere is never contained in another ref; with `worktrees.remove_merged` on (the default, #210), `remove(id, { landed })` counts the work a landed commit contains as kept, so a squash-merged task's checkouts can go (see below). Removing an unknown id is a no-op. For a checkout deleted by hand, the same checks run on its Git admin directory, and only that directory is deleted (never a repo-wide `git worktree prune`).
- A merge marks its source worktree, and the staging worktree of a squash, busy with marker files under the worktree root. Removal takes a per-worktree lock file there, then skips busy worktrees, so garbage collection by any manager on the repository cannot remove a worktree mid-merge. Markers and locks left by a process that died, or held for over an hour (a reused PID), are ignored, and a merge waits up to 5 s for a removal that may only be checking its worktree; liveness is checked by PID, so managers sharing a worktree root must share a PID namespace (not a container and its host), or one may clear the other's markers and fail its merge (no commits are lost). The removal lock holds a per-holder token, is created by linking a complete file into place, and is released only by its holder. Callers stop Workers before cleanup; path-based operations protect the `.git` entry from symlink following but assume the worktree directory itself is not concurrently renamed or replaced.
- Removing merged worktrees (#210, `worktrees.remove_merged`, default on; `tacet init` asks, `--keep-merged-worktrees` turns it off). The Mini-conductor's sweep removes them, not `WorktreeManager.gc()`, which knows nothing of the event log. The user merges outside Tacet, so the Mini-conductor looks at start and then every 10 minutes: for each completed task with a published result (`SummaryPacket.published`) and a Worker checkout left, it checks whether the result landed in the task's target: the branch recorded in `task.target` when the task started (#219; for older tasks, the one `worker.started.baseBranch` its checkouts agree on): merged (the branch contains it) or squash-merged (one of the branch's newest 1,000 non-merge commits since the fork point has the same `git patch-id --stable` as the whole change). It reads the repo's own refs and objects only, with the repo's own config, and never fetches: a partial clone (which would fetch missing objects while diffing) is never checked, so its checkouts stay. A result found not landed is not checked again until its target moves. It then records `task.landed` once and removes each checkout not in use, with the result commit as landed, together with each commit a session that ran in that checkout integrated and then replaced with its own next integration as an amend: the same first parent, and the Worker's own HEAD reflog made it with `commit (amend)` or a rebase squash or fixup, as in a fix round (owner decision on #210). A failed attempt's or another sub-task's work never counts, nor a new commit after a reset: that work is abandoned, and abandoned work is always kept until forced. An integrated commit covers the history it brought in. Once `task.landed` is recorded it is trusted, even if the target is later reset: the result branch `tacet/<task>/result` still holds the work. Reflog reachability alone never counts: the checks above still keep a checkout with local files, never-integrated private commits, or work none of those commits contain. A rebase merge of several commits is not detected, and such checkouts stay. With the setting off it does no git work and records nothing.
- Worker commits are brought into the shared object store and a `refs/heads/tacet/<worktree-id>` integration ref through the existing `integrateWorktree` path before conflict checks or merge preparation. The Worker never writes that shared ref. PR and manual strategies return the integration ref and Worker HEAD SHA for review or user handling. Squash-to-branch stages the integrated result, in the index and the working tree, in a separate managed worktree on its own `tacet/<staging-id>` branch based on the target; it does not change the target, commit, or push. After a merge the Worker's work lives only on those `tacet/*` branches, so both worktrees are kept until it is merged elsewhere or removed with `force`. Conflict checks do not modify the target branch.

## 3. Key interfaces (sketch)

```ts
interface AgentAdapter {               // packages/core/src/adapter/types.ts (#10)
  id: string;                         // "claude-sdk", "codex-app-server", "acp", "pty:claude", "pty:<preset>"
  capabilities(): AdapterCapabilities; // streaming, liveInput, approvals, interrupt, resume, fork, usage, modelSwitch, injectContext, effortSwitch?, contextSizes?
  start(opts: SessionOptions): Promise<SessionHandle>;   // resolves when ready; opts.resume continues or forks a vendor session; model, effort and contextWindow form the SessionProfile
  send(h: SessionHandle, input: UserInput, opts?: { model?: string; effort?: Effort }): Promise<void>;
  interrupt(h: SessionHandle): Promise<{ stillQueued?: string[] }>;
  respond(h: SessionHandle, req: ApprovalId, decision: ApprovalDecision): Promise<void>;
  close(h: SessionHandle): Promise<void>;
  events(h: SessionHandle): AsyncIterable<AgentEvent>; // normalized
  status(h: SessionHandle): SessionState;
  injectContext?(h: SessionHandle, text: string): Promise<void>;
  terminal?(h: SessionHandle): AgentTerminal; // PTY adapters (#15): read-only scrollback + live output for `tacet attach`; never persisted, never events
  discard?(vendorSessionId: string, cwd: string): Promise<void>; // #153: the closed session will never be resumed; drop what the adapter keeps for that
}

type AgentEvent =                     // zod source: packages/core/src/schema/agent-event.ts
  | { t: "message.delta"; text: string }
  | { t: "tool.call"; id: string; name: string; input: unknown }   // input redacted
  | { t: "tool.result"; id: string; ok: boolean; summary?: string }
  | { t: "approval.request"; id: string; summary: string; toolName?: string;
      options?: ("allow_once" | "allow_always" | "reject" | "cancel")[]; requestedGrant?: unknown }
  | { t: "usage"; inputTokens: number; outputTokens: number; contextUsed?: number; contextMax?: number;
      costUsd?: number; model?: string; source: "reported" | "estimated" }
  | { t: "status"; state: "running" | "idle" | "waiting_input" | "auth_required" | "cancelled" | "error" | "done";
      message?: string }
  | { t: "escalation"; question: string; options?: string[]; urgency: Urgency; context?: string; contextRef?: string };

// The answer to an approval.request. allow_always is session-scoped unless persist is true.
type ApprovalDecision = { kind: "allow_once" | "allow_always" | "reject" | "cancel"; persist?: boolean;
  message?: string; updatedInput?: unknown; grant?: unknown };
```

The shared schemas (`AgentEvent`, `Task`, `Escalation`, `Decision`, `HandoffPacket`, the event envelope and the A2A extension metadata) are zod 4 schemas in `@tacet/core`, exported as JSON Schema 2020-12 in `packages/core/schema/v1/` (#5, [ADR-003 §7](adr/003-wire-protocols.md#7-json-schema-stubs-acceptance-item-deferred-to-the-scaffold)). On `usage`, token and cost fields are per-call deltas (adapters convert cumulative vendor totals), `contextUsed`/`contextMax` are gauges, and context and cost are optional because not every vendor reports them ([capability matrix §7](adapters/capability-matrix.md)). `ApprovalDecision` (an adapter's answer to a tool-approval request) is distinct from `Decision` (a recorded answer to an escalation, reused as precedent). Receivers parse agent events with `parseAgentEvent`, which ignores unknown kinds. Enum fields read an unknown value as their documented fallback, for example `urgency` as `normal` and `kind` as `reject` ([ADR-003 enum addendum](adr/003-wire-protocols.md#addendum-2026-11-09-enum-evolution-2)).

Every adapter must pass the conformance bench in `@tacet/core/testing` (`runConformance`), run against recorded fixtures or a local mock, never live vendor calls in CI. Its probes compare declared capabilities with observed behaviour and report `drift` when they disagree; P0 probes (start, valid events, stream, usage, approval round-trip, interrupt, close) gate CI, and P1 probes (live input, resume, injected context, model switch, effort, context sizes) only report (#10, after Omnigent's harness bench, ADR-001). An adapter that cannot honour a profile field (an effort level the model lacks, an unlisted context window) throws `ProfileRefusedError` rather than ignore it (#110).

All events go to an append-only **event log** (SQLite) → UI timelines, replay, audit, cost.

The log is `openEventStore()` in `@tacet/core/node` (#6). It stores each envelope verbatim, is idempotent on the envelope id, and blocks `UPDATE`/`DELETE` with triggers. State is rebuilt with pure projections (`tasksProjection` in `@tacet/core`). Retention deletes old transcript-grade events (`agent.message`, `agent.tool`, `agent.approval`, `agent.status`, `agent.escalation`) and keeps every summary-grade event, so task state replays exactly after compaction. Driver: `better-sqlite3`, chosen under [ADR-002](adr/002-language-runtime.md) decision 5 because `node:sqlite` is still a release candidate (Stability 1.2) in Node 24 and 26 as of 2026-11-09; callers use the `EventStore` interface, so moving to `node:sqlite` once it is Stable touches one file.

Every state change is wrapped in an **event envelope** before it is stored or forwarded: `{v, id (ULID), ts, source, repo?, taskId?, sessionId?, correlationId?, causationId?, type, data}`. `AgentEvent` above is the payload of the `agent.*` envelope types (for example `agent.message.delta` and `agent.usage`). The other namespaces are `task.*`, `escalation.*`, `decision.*`, `handoff.*`, `worker.*` and `budget.*`. Worker lifecycle events are summary-grade and kept by retention: `worker.started` (`WorkerStarted`: adapter, model, `workspaceId`, `attempt`, `previousSessionId` for a replacement session, `baseCommit` when a new checkout starts from its dependencies' work, #134), `worker.profile` (`WorkerProfile`: the model, effort and context window the policy chose, with `reasons` keyed by part, written in the same append as `worker.started`; written again with `refused` when the adapter refuses a part, then once more for the profile the session runs on, so the last one for a session is in force unless it is refused, when no session ran, #110), `worker.vendor_session` (the vendor's session id, once known), `worker.nudged`, `worker.integrated` (the Worker's commit is in the repo under `refs/heads/tacet/<task>`, #119), `worker.verification` and `worker.review` (one check of a sub-task's integrated commit: a `verify` command's result, and the reviewer agent's verdict as counts, #19), `worker.approval` (a Worker's approval request the Mini-conductor refused under the interim policy, with the reason, #200; allowed ones are transcript-grade `agent.approval.decision`), `worker.throttled` (a Worker went over its limit on `escalate` or `record_decision`, by default 6 and 30 per 10 minutes; the calls over it get a tool error and create nothing, #121) and `worker.ended` (`reason`: `finished`, `failed`, `stuck`, `restart`, `canceled`, `handoff`; unknown reads as `failed`; `failed` and `stuck` count against `workers.max_attempts`, the others do not). `worker.started` also carries `baseBranch`, the local branch a new checkout started from. `task.landed` (`TaskLanded`: `commit`, `target`, `how` `merge` or `squash`, `landedAs` for a squash; caused by the task's `task.result`) records that a task's published result landed in its target (#210). `task.target` (`TaskTarget`: `branch`, absent for a detached HEAD, and `commit`) records, once, before a task is planned, the repo's checked-out branch and commit: every sub-task without dependencies starts from that commit, so switching the main checkout's branch mid-task moves none of them, and the branch is the target its result lands in (#219). The planner plans at that commit too. If the target cannot be read (an unborn branch, a git failure), planning fails with that message rather than fall back to a moving branch. No ref holds the pinned commit: live checkouts keep it, but if the branch is rewritten and git prunes it, a later fresh checkout of the task fails to start (a ref to hold it: #236). A Mini-conductor writes `worker.started` before it starts the vendor session, so a crash in between still leaves a record, and rebuilds its Worker pool from these events on restart. They name workspaces by id, never by path, because they are forwarded to the Conductor. Receivers ignore unknown fields and unknown event types. The full envelope is in [ADR-003 §1](adr/003-wire-protocols.md#1-one-transport-envelope-and-one-event-envelope).

**Merge semantics** (#7, `@tacet/core` `mergeConfig`, loaded by `loadConfig` in `@tacet/core/node`):

- Precedence, lowest first: built-in defaults, user, repo, local, task. Objects merge key by key; a higher layer's scalar or array replaces the lower one.
- The task layer may not set the tier bounds (`tiers.*.models`, `max_effort`, `max_context_window`), and the merged `model` and `effort` must lie within them (#110).
- The task layer may only **lower** `workers.*`, never raise it, because the Worker pool is repo-wide (owner decision, 2026-11-09): a raise is a config error. It may not set `workers.env` at all, nor `worktrees` (#210: cleanup is the user's and the repo's call), nor `verify` (#19: a task could turn every check off, or run shell outside any Worker); it may turn `review.enabled` on, never off, and may not change `tiers.review` or declare a tier's `vendor`, and the committed repo layer may not name a secret-looking variable in `workers.env.pass` (#147, §6).
- Exception: `policies`, `escalation.always_ask` and `workers.env.pass` are **unioned** across layers, so a repo or local file cannot silently drop a safety rule or a toolchain variable set elsewhere. Policy evaluation (#25) checks task, local, repo, then user rules, and a `deny` anywhere wins.
- Config is validated strictly: an unknown key or enum value is an error with file, line and column, and all errors are reported at once.
- Secrets never appear in config. Literal credentials (API keys, tokens, private keys) are rejected without echoing them; use `{ env: NAME }` or `{ keychain: service/account }`. A keychain reference is read at startup from the OS keychain (#160): `security find-generic-password` on macOS, or `secret-tool lookup` (a Secret Service keyring such as gnome-keyring) on Linux. It is never unlocked by Tacet; the value must be printable ASCII (one trailing newline is dropped); and a missing, locked or unreadable item is a startup error naming its config path, never a value (details: [spike #160](adapters/spikes/160-keychain/README.md)). A higher layer replaces a secret reference whole (`secrets.*`, `agents.*.env.*`), so switching from `env` to `keychain` never keeps both, and the merged result is validated against the schema again.
- `tacet config explain [--json]` prints every effective value with the layer and file that set it. The output is deterministic.

**Setting up a repo** (#20). `tacet init [--worker ADAPTER] [--model MODEL] [--keep-merged-worktrees]` writes the repo layer `.tacet/tacet.yaml` and `.tacet/.gitignore` (which ignores `local.yaml`), each only when it is absent, so a re-run changes nothing. It writes nothing outside `.tacet/`: not the root `.gitignore`, not `~/.tacet`, and not the repo's own agent files (`CLAUDE.md`, `AGENTS.md`, `.claude/`). The generated config sets `tiers.worker` (default `claude-sdk`; `codex-app-server`, `acp:gemini` and `acp:claude-acp` on request) and its `model` when given or typed at the prompt; it never guesses a model id. It asks once whether to remove Worker checkouts after their work is merged (`--keep-merged-worktrees` answers no without asking; `--json` never asks); only a no is written as a setting (`worktrees.remove_merged: false`), the default as a comment, so the committed file never fixes a preference by accident (#210). `tiers.mini`, `verify` (suggested from `package.json` scripts) and `review` are written commented out: a Worker checkout is a fresh worktree, so a verify command that needs installed dependencies would fail there. Init reports which adapters can run (the bundled ones, or the ACP agent's command on `PATH`) and whether each API-key variable is set, by name: it never reads values, never reads vendor login or OAuth files and never runs a vendor CLI (owner decision on #209). Each file starts with a header carrying a hash of its contents, so `tacet uninstall` (a preview; `--apply` acts) removes only the files init wrote that nobody changed or committed, then `.tacet/` if it is empty (a committed `tacet.yaml` is the team's, so only `--purge` removes it; owner decision on #209). `--purge` removes all of `.tacet/` after copying it to `~/.tacet/backups/<repo>-<hash>/uninstall-<time>/`, and the repo's run state `<state_dir>/<repo-hash>/` (#211): the preview lists it, its event log and each Worker or planner checkout, marking those the worktree manager would keep (unintegrated work, local files). The preview writes nothing (no lock, no marker cleanup) and lists every entry of the state dir, which all goes: the event log, Worker homes such as Codex's, the lock. With `--apply` it takes the repo's run lock as `tacet run` does (refusing while a run holds it, taking over a stale one), ends any Worker processes a crashed run left behind, removes each checkout through `WorktreeManager.remove` with `keepBranch` (one with unintegrated work only with `--force`; otherwise it is named and nothing else is removed). Because every `tacet/*` branch is kept, work one of them holds counts as kept (owner decision on #211): their tips are passed as `landed`, never the checkout's own `tacet/<id>` branch, and the preview names the branches holding each removed checkout's work; local files and never-integrated commits still need `--force`, then the rest of the state dir, the lock last. It never runs `git worktree prune` (repo-wide: it would also prune the user's own worktrees whose paths are missing), keeps the state dir if git still lists a worktree in it, refuses when the config cannot be read (the state may live elsewhere), and keeps every `tacet/*` branch. Both refuse a repo whose `.tacet/` is, or overlaps, the user directory `~/.tacet` (a home directory kept in git).

**Session profile** (#110). Each Worker session runs on a profile, `SessionProfile { model, effort?, contextWindow? }` in `@tacet/core`. The Mini-conductor chooses it with `chooseProfile` (`packages/mini/src/daemon/profile.ts`) from the tier and its bounds, the sub-task and its failed attempts:

- **Model:** the tier's `model`, else the first of `models`.
- **Effort:** the tier's `effort`. With `escalate_effort_on_retry` it rises one level per failed attempt, up to `max_effort`. Levels are ordered `none` < `minimal` < `low` < `medium` < `high` < `xhigh` < `max` < `ultra` (`EFFORT_LEVELS`).
- **Context window:** a cost lever, off by default. Tacet hands off at the `handoff` threshold (§2.3, #31). It opts into a larger window only for a sub-task the planner marked `indivisible`, when `max_context_window` allows it and the adapter lists such a size (`contextSizes`).

Every choice is written as a `worker.profile` event with a reason for each part, next to `worker.started`. A profile outside the bounds fails the sub-task before any session starts.

Adapters declare what they can honour: `effortSwitch` (`per-turn` or `per-session`) and `contextSizes`. Anything they cannot honour they refuse with `ProfileRefusedError` instead of ignoring it (capability matrix §7):
- Claude refuses levels the model lacks, and the 1M window outside Sonnet 4/4.5.
- Codex checks every level against `model/list` and refuses every window.

When an adapter refuses a part, the Mini-conductor logs it and starts the session again without counting a failed attempt. A refused effort steps down one level, but never below the tier's `effort`; below that, the model's default effort is used, which is the vendor's choice and is not checked against `max_effort`. A refused context window falls back to the default. A refused model has no fallback, so the sub-task fails at once. The `mini` tier (the planner) does not go through the policy and takes no bounds. Budget headroom is not an input yet: the cost ledger is #35. Task-type rules and per-task overrides are #33.

A fork the adapter will not do for a session is refused before anything is left running with `ForkRefusedError` (#228): `fork: 'none'` (PTY), or a declared `native` fork that the vendor does not offer for that session (an ACP agent whose `initialize` does not advertise `session/fork`). Other start failures keep their errors, so a caller can tell the refusal apart and seed a new session from a HandoffPacket instead. The Mini-conductor does not fork sessions today.

## 6. Security & auth principles
Local servers ([ADR-003 §3, §5, §6](adr/003-wire-protocols.md#3-auth-token-handshake-all-local-servers)):

The building blocks live in `@tacet/core/node` (`packages/core/src/node/auth/`, #77): `writeRuntimeFile`/`readRuntimeFile`, `listenLoopback`, `checkHostAndOrigin`, `HelloGate`, `OneTimeCodes`/`BrowserSessions`/`exchangeCode` (session token in the response body, never a cookie; `HelloGate` checks it for `role: "ui"` via `verifyBrowserSession`), `WorkerTokens`, and a `Secret` wrapper that prints `[redacted]` everywhere except `reveal()`. The daemons wire them into their HTTP and WebSocket servers.

- **Binding.** The Conductor and each mini-conductor bind `127.0.0.1` and `::1` on an OS-assigned port. Remote or LAN access is an explicit opt-in (`remote: true` plus TLS) and is out of scope for v0.
- **Token.** Each daemon generates a 256-bit token on start and rotates it on every start. The token is written, with the pid, port and protocol versions, to a runtime file in `~/.tacet/run/` that only the user can read (mode 0600 on POSIX). It is never inside a repo, and it is never logged or put in events.
- **Browsers** never get the daemon token, and no cookie is set ([ADR-003 §3.4 addendum](adr/003-wire-protocols.md#addendum-2026-11-09-browser-session-without-cookies-34)). `tacet open` opens `http://127.0.0.1:<port>/#code=<one-time-code>`. The page exchanges the code (single use, 60 s lifetime) at `POST /auth/session` for a browser session token, keeps it in memory only (never `localStorage` or a cookie), sends it in the `tacet/hello` frame on the WebSocket and as `Authorization: Bearer` on HTTP calls. An upgrade without a daemon bearer token may only hello as `ui` with a valid session token, so a local process cannot claim the `cli` or `mini` role, and a present `Origin` must always match. The upgrade and the code exchange require `Origin`; session-token HTTP calls may omit it only on GET and HEAD, where browsers do not send it outside CORS. A missing `Origin` is not proof of same-origin (cross-origin no-cors GETs omit it too): the session token is the control, so session GET/HEAD routes must not change state. Daemons use `authorizeSessionRequest`, which validates the token and takes the method from the request line.
- **Host and Origin.** Requests are rejected unless `Host` is `127.0.0.1`, `[::1]` or `localhost` with the server port (DNS-rebinding defence). A present `Origin` must match the served origin; when it is required is set per request kind (`RequestAuth`: `browser`, `session`, `bearer`).
- **Hello.** The first frame on any socket must be `tacet/hello`. Any other method before hello closes the socket.
- **Prompts** (#15): no prompt Tacet sends a Worker may start with `/` or `!`: an interactive CLI runs those as a slash or shell command, and Claude Code runs `!` with no hook or approval at all (capability matrix §1). Tacet refuses either one even after spaces, control or invisible characters (`promptCommandPrefix` and `assertSafePrompt` in `@tacet/core`): the Mini-conductor asserts it where it composes prompts, and the PTY adapter refuses such input.
- **Workers** get their own MCP token, bound to `{workerSessionId, taskId}` and revoked when the session closes. Tools take no `taskId` or `workerId` argument, and the token never appears in events ([ADR-003 §6](adr/003-wire-protocols.md#6-workers--mini-conductor-mcp-tool-surface)).

Vendor auth and billing:

- Never store, log, proxy or copy vendor OAuth or subscription tokens. Launch vendor CLIs and SDKs under the user's own login or API key.
- **Default auth routing** (owner decision, 2026-11-09): prefer the API key for parallel or unattended Workers, and use the user's subscription login for interactive or single sessions. Only the interactive route is configurable: `auth.unattended` accepts only `api_key` (owner decision on #65). The same policy applies to Codex (#12): an API key for unattended or parallel Workers, and the user's own Codex login only for interactive use. Tacet never implements `chatgptAuthTokens`. Tacet never runs parallel Workers on one subscription; see [`docs/RESEARCH.md` §7](RESEARCH.md#7-auth-billing-and-terms-important-constraint).

Accepted residual risks (owner decision, 2026-11-09):

- **Verify commands run Worker-written code outside any vendor sandbox** (#19). The commands are the user's, but what they run (`package.json` scripts, test files) is the Worker's, run as the user. For Claude Workers (SDK, ACP and PTY) and Gemini this adds nothing: Tacet runs them without a sandbox today. For Codex Workers (native, and `acp:codex-acp` in Codex's `workspace-write` mode) it would: their sandbox keeps the shared `.git` read-only for them, and a test they wrote could plant a hook there when verify runs it. **Pending the owner's decision**: until then, Codex Workers are not verified (`VERIFY_CODEX_WORKERS = false` in `@tacet/mini`, a one-line switch). The worker sandbox (#53) should cover verify too. Verify output is Worker-controlled text: it reaches the Worker as feedback and, cut to 2 KB and labelled as command output, the Conductor in `verification.notes`.
- **Workers can read `~/.tacet/run`.** Workers run as the same OS user, so file modes alone cannot keep the daemon tokens in `~/.tacet/run/*.json` from them. Until the worker sandbox (#53) denies that path, a worker that reads the file can act as the Mini-conductor or Conductor. The sandbox profile closes this. The same holds for sibling Workers' MCP tokens in `~/.tacet/run/mcp/` (accepted interim risk, ADR-003 addendum): a Worker that reads one can act as that Worker until #53 denies the path; each file is deleted when its session closes, and the Mini-conductor revokes the token when the Worker ends.
- **The one-time code is visible in the process list.** `tacet open` passes the URL (code in the fragment) to the browser launcher, so `ps` shows it to processes of the same user. Accepted: the code is single use, expires after 60 s, and only same-user processes can see it.
- **The reviewer agent reads Worker-written text** (#19). The diff it reviews is the Worker's, and can try to talk it into approving; review runs only after the `verify` commands pass, so at worst a false approval lets through work that already passed them, and it never makes failing work pass. The diff goes to the review tier's vendor, redacted of key-shaped strings (a pattern match, not a guarantee). Its findings reach only the Worker, as untrusted feedback: events, `verification.notes` and the Conductor get counts by severity, never their text, and a fresh attempt after a failed review is told the counts. The reviewer runs no Worker code: every tool it asks for is refused, and it works in an empty directory of its own, so no settings, hooks or instructions the Worker committed are loaded for it.
- **Worker processes after a crash** (#127): every Worker session gets a random marker, `TACET_WORKER_MARKER=<uuid>`, in its vendor process's environment, which the processes it starts inherit (Claude Code's Bash tools included, even background ones in sessions of their own). The Mini-conductor writes the marker to a 0600 file next to its lock (`<lockPath>.workers`, never in events) before the session starts, and drops it once the adapter has closed the session. On start, before anything resumes, it ends every process of the user whose environment holds a recorded marker (Linux: `/proc/<pid>/environ`; macOS: `ps -E`): SIGTERM, then SIGKILL after 5 s. A process found by its marker is then followed by pid until it is gone (its start time checked before every signal), so a process is never taken for gone only because its environment can no longer be read. A reused pid cannot carry a marker it never saw, so pid reuse needs no further guard. Long-lived services a Worker started (a tmux server, a build daemon) carry its marker too and are ended after a crash, while a clean close leaves them alone. So do helpers a CLI detaches (#171): a clean close ends the CLI, not what it detached (verified live on Linux; on macOS the same holds by the same mechanism, environment inheritance and the `ps -E` sweep, not run). Interactive Codex's managed `codex app-server` daemon is one, and it is shared by every Codex session with the same `CODEX_HOME`, so it is not swept at a clean close: sweeping one session's marker cut off a concurrent session that used the same daemon (live on Linux, `docs/adapters/spikes/168-resume-scope/codex-shared-daemon.mjs`). Codex PTY presets set `-c features.daemon_auto_start=false` so it is never started (verified live on Linux: no daemon, resume unchanged); the app-server routes (`codex-app-server`, `acp:codex-acp`) left no daemon in any test run. Not covered: a process that clears or overwrites its environment (`env -i`, setproctitle, as a Postgres a test suite starts does), a process whose environment the user cannot read (setuid, non-dumpable), and Codex's tool processes until Codex's environment handling for them is verified. Until the sandbox (#53) denies the state directory, a Worker that writes the file could get processes ended that carry markers of its choosing, which only Worker processes do.
- **Worker MCP config files** hold the worker's token. Adapters write them outside the worktree at mode 0600 and delete them when the session closes, so they cannot be committed (#11–#15). The handling is shared in `@tacet/core/node` as *session files* (`writeSessionFile`, `removeSessionFile`, `sweepStaleSessionFiles`), for any per-session file that holds a Worker secret, such as the PTY adapter's hook settings (#15). Each Mini-conductor process writes into its own `~/.tacet/run/mcp/<pid namespace>-<pid>-<hash of its start time>/` (`unknown` in place of the hash when it cannot read its own start time); the Claude adapter removes, at its first session, the directories of owners in its pid namespace that are no longer running (a reused pid has another start time; an owner whose start time cannot be read, or that wrote `unknown`, counts as running while its pid exists), and reports only how many files went (#108). Files written directly into the directory by earlier versions have no known owner and are left alone.
- **PTY hook tokens** (#15): the PTY adapter (`pty:claude`) runs interactive Claude Code with its hooks POSTing to a loopback endpoint of the adapter, authenticated by a per-session bearer token. The token sits as a literal header in the session's `--settings` file, a 0600 session file outside the worktree (no environment variable, so the Worker's own tools do not inherit it); identity comes from the token only. Until the sandbox (#53) denies `~/.tacet/run/mcp`, a Worker that reads a sibling's settings file can forge that sibling's hook events, e.g. a `Stop` that makes it look idle early (accepted interim risk, as for MCP tokens). PTY Workers authenticate like SDK Workers (an API key, or a cloud provider route the user chose), never with a subscription login: the PTY route is not a way to run unattended Workers on one. A PTY Worker runs with `--permission-mode manual`, never auto or bypass, and its `PreToolUse` hook answers `ask` for every tool but Tacet's own `mcp__tacet__*`, so every other tool call, read-only ones included, reaches Tacet as a `PermissionRequest` (the Mini-conductor's policy until #25). Each session gets its own `CLAUDE_CONFIG_DIR` under `~/.tacet/state/<repo-hash>/claude-pty/<session>` with onboarding done, the worktree trusted (as the Agent SDK treats every folder) and the key approved by its last 20 characters, as Claude Code records it; `--setting-sources ""` and `--strict-mcp-config` keep the user's and the repo's settings, hooks and MCP servers out (verified live with a hostile `.claude/` and `.mcp.json`). Prompts are typed as one bracketed paste with control characters removed; a prompt starting with `/` or `!` is refused, since Claude Code would run it as a slash command or, with no approval at all, as a shell command. Turn-scoped hooks of another turn (by `prompt_id`), or of a cancelled one, change nothing. A turn is matched to the prompt Tacet typed by the `UserPromptSubmit` prompt text (with Claude Code's `<pasted_content>` wrapper for multi-line pastes removed) as well as by `prompt_id` (#190): if an Esc did not take, the prompt typed next joins the running turn under that turn's `prompt_id` and then runs under a new one that no `UserPromptSubmit` announces, so the adapter waits for the joined turn's `Stop` and takes the next new id as the prompt's turn (never a subagent's), and the cancelled turn's reply is never credited to it. A cancelled turn whose `UserPromptSubmit` arrives only after the cancel stays cancelled; the same text sent again waits (up to 3 s) for that late submit first (a submit later still is taken as the retry's, an accepted edge); a hook without prompt text falls back to matching by `prompt_id`. A joined prompt whose own turn does not show within the acknowledgement timeout after the joined turn's `Stop` ends in `waiting_input`. A session counts as started once `SessionStart` has arrived and the interface has turned on bracketed paste (it takes input from then on); `close()` lets Claude Code exit by itself first (Ctrl-D twice), so the last turn stays resumable, then ends the process group. Those directories are removed (#153) when a new session fails to start, when the Mini-conductor discards a session it will never resume (one that ended for any reason but `restart`, a restart it does not resume after all, or a resume that failed), and otherwise once nothing has written to them for `events.retention.transcript_days`. That sweep runs when the adapter starts its first session for a repo and skips the adapter's open sessions; it could remove the directory of a session idle that long that another process, such as a manual run outside the Mini-conductor, still has open (accepted). The repo is the adapter's `repoRoot` (`buildWorkerAdapters` passes it), else the main checkout of the session's git worktree, read from the worktree's own `.git` pointer. A Worker that rewrites that file can only misplace its own checkout's session state under another repo's key (where the sweep still finds it) until `tacet up` passes `repoRoot`.
- **ACP session files** (#232): an ACP agent with a home of its own (`<repo state dir>/acp-<agent>`, #150) keeps its sessions' transcripts there, and they can hold the contents of files a Worker read. A spec that lists where (`AcpAgentSpec.sessionFiles`; claude-acp: `projects/*/<id>.jsonl`, `projects/*/<id>/`, `file-history/<id>/` and `debug/<id>.txt`, read from the Agent SDK 0.3.318 binary claude-agent-acp 0.101.0 pins) has them removed by `discard()` when the Mini-conductor ends a session for good, as for PTY above; an id without a transcript removes nothing, so a shared directory such as `projects/<p>/memory/` is never taken for a session. They are also swept, sessions with a transcript untouched for `events.retention.transcript_days`, once per adapter, when it first prepares the home. The sweep skips sessions open or being resumed in this adapter; a session kept for a restart whose resume has not started yet is swept if it is that old, and its resume then fails and starts afresh, and, as for PTY, a session another process (a manual run) still has open could be removed (both accepted). The project directory is matched, never computed from the cwd, and only real directories of the user are descended. Agents without the list (gemini; codex-acp, which Workers may not use) keep their sessions until it is added. The Claude SDK adapter keeps its transcripts in the user's own `~/.claude`, which Tacet never touches (#237).

Other:

- **Platforms** ([ADR-002](adr/002-language-runtime.md), 2026-11-10 addendum): macOS and Linux (Ubuntu), and Windows via WSL2, where Tacet runs inside the WSL2 Linux distro as on Linux, with its repos in the distro's own filesystem: setup and caveats in [WSL2.md](WSL2.md); `tacet run` warns when the repo or the state directory is on a Windows drive inside WSL (`wslPathWarnings` in `@tacet/core/node`); CI covers WSL2 only in the experimental, non-required `wsl2` workflow (#193). Native Windows awaits an ADR (#194).
- Worktree isolation by default; optional OS sandbox later.
- **`acp:codex-acp` is refused for unattended sessions** (interim default until the owner decides #183): it marks every session directory trusted itself, after any config Tacet can pass, so a checkout's `.codex/config.toml` (an MCP server command) and `AGENTS.md` would apply, whoever wrote them (observed live in #181). `AcpAgentSpec.workerRefused` says why; `buildWorkerAdapters` rejects a Worker tier or `workers.per_adapter` cap that names it, or a custom `agents.<slug>` whose command runs it (by name, path or npm package), and the Mini-conductor and the planner refuse an adapter built on the built-in codex-acp spec however they get it. Direct interactive use of the adapter is unchanged. A wrapper script that hides the command is not caught. Use `codex-app-server` instead, whose unattended Workers are kept untrusted (#181, below).
- **Codex Worker isolation** (owner decision, 2026-11-09; #116):
  - The Codex sandbox's writable roots gain the Worker's *own* worktree git directory (the one `git rev-parse --git-dir` names for that worktree), and no other, so `git commit` works without an escalation each time. A commit also writes objects and a branch ref to the repo's shared `.git`, so (owner decision, option B) the Worker commits on a **detached HEAD** (HEAD is per-worktree) into its **own object store**: the adapter sets `GIT_OBJECT_DIRECTORY=<worktree git dir>/objects` and `GIT_ALTERNATE_OBJECT_DIRECTORIES=<repo>/.git/objects`. The shared `.git` (refs, objects, config, hooks) stays read-only to the Worker. The Mini-conductor integrates the commits outside the sandbox (owner decision, 2026-11-09; #119): after every Worker turn (before verification, and before the sub-task waits on the user), it copies the Worker's loose objects into a snapshot it owns (regular files with object names only, never through a symlink or FIFO, size-capped; the Worker store's alternates and packs are never read), packs the objects reachable from the Worker's HEAD that no branch or tag has, checks them with `index-pack --strict` into a directory of its own (broken or forged objects are rejected and leave nothing behind), moves the checked pack into the shared store, and runs `update-ref refs/heads/tacet/<task>` (compare-and-swap), recording `worker.integrated` (`integrateWorktree` in `@tacet/mini`). Every git command runs asynchronously with a timeout. A turn without a commit of its own integrates nothing. On Linux the Worker's object store is walked through open directory descriptors (`/proc/self/fd`), so a directory swapped for a symlink mid-copy is never followed; macOS has no such path and only re-checks each directory's identity after opening, so a Worker that wins a swap-and-swap-back race could have well-formed objects from another repo the Mini-conductor can read copied in (accepted residual risk; `index-pack --strict` still rejects anything malformed). A checkout that fails the integrity checks below is not touched: the run ends (not counted as a failed attempt) and the user is asked; after the answer the sub-task runs again in a fresh checkout, and the refused one is kept for inspection.
    - **Everything in the Worker's worktree and its git dir is untrusted** once the Worker has run, and a running Worker can change it at any moment (background processes outlive turns). A rewritten `commondir`, `.git` pointer file or `config.worktree` would make git, run later *outside* the sandbox, load config and hooks the Worker wrote; a `logs/HEAD` symlink would make a ref update append to any file. So, before and during any git command outside the sandbox (the adapter's detach at start, the Mini-conductor's integration): the worktree is checked against the trusted repo root by reading its pointer files (`workerWorktree`, in `@tacet/core/node` and shared by the Codex adapter and the Mini-conductor); git runs with `GIT_DIR`, `GIT_COMMON_DIR` and `GIT_WORK_TREE` set explicitly, so a later forged `commondir` is ignored, with only PATH and HOME besides (`trustedGitEnv`), and with hooks, fsmonitor, reflogs and the commit-graph off (`SAFE_GIT_ARGS`). The adapter writes the detached `HEAD` itself (temp file and rename) instead of running a checkout or `update-ref`. A repo with `extensions.worktreeConfig` (e.g. after `git sparse-checkout`) is refused: git would read `config.worktree` from the Worker-writable git dir.
    - Worker-side commands that write shared refs (`git checkout -b`, `git branch`, `git stash`) fail in the sandbox; whether that becomes an escalation depends on the approval policy. `git checkout <existing branch>` works (HEAD is per-worktree), but the next commit then fails on the shared ref.
    - Until a Worker's commits are integrated, the main repo's `git gc`, `git prune` and `git fsck` fail on that worktree's HEAD (`bad object worktrees/<wt>/HEAD`), and so does a `git push` *into* the repo (its connectivity check walks every worktree HEAD): one unintegrated Worker blocks pushing any other Worker's commits. Nothing is lost. That is why integration copies objects and runs `update-ref` from the main repo instead of pushing into it (#119).
    - The object-dir variables apply to every repo the Worker touches, so a submodule, a `git clone` or a nested repo inside the worktree does not work for unattended Codex Workers yet.
  - Unattended Codex Workers get their own `CODEX_HOME` at `~/.tacet/state/<repo>/codex`; interactive sessions keep the user's `~/.codex`. The user's `config.toml` customisations (including their MCP servers) therefore do not apply to unattended Workers.
  - Codex `features.plugins` is off for unattended Workers, so a Worker start never syncs plugins from GitHub.
- **Worker environment** (#147): a Worker starts with an allowlist of the user's environment, not all of it (`workerEnv` in `@tacet/core`): a base set (PATH, HOME, user, locale, terminal, temp dirs, proxies, CA bundles), toolchain locations (`JAVA_HOME`, `GOPATH`, `CARGO_HOME`, `NVM_DIR`, `VIRTUAL_ENV`, ...), the adapter's own vendor variables, and `workers.env.pass` (names, or prefixes ending in `*`). A prefix, whether an adapter's (`ANTHROPIC_*`, `CODEX_*`, `GEMINI_*`) or the user's, never passes a secret-looking name (`*_TOKEN`, `*_KEY`, `*_SECRET`, `*_PASSWORD`, `*_PAT`, ...): the vendor's own key variables pass by name, and a cloud credential chain the user chose passes whole (`AWS_*` when Claude Code runs on Bedrock). Otherwise a secret-looking variable passes only by its exact name, from the user or local layer, never the committed repo layer, and never from a task. Tacet's own per-session variables (`TACET_WORKER_MARKER`, the session's MCP settings) are added after filtering. Adapters report the names (never values) of dropped variables through a callback, not in events. Interactive sessions may inherit the user's whole environment: an interactive Codex session does by default, a Claude or ACP session only with `envPolicy: { inherit: 'all' }`. `SSH_AUTH_SOCK` and GPG agent variables are not in the base set, so unattended Workers do not sign commits or push over SSH with the user's agent unless the user passes them. Inherited `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` are dropped on purpose (a value can carry `http.extraHeader` credentials); the user's `~/.gitconfig` still applies through `HOME`, and commit identity variables (`GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `EMAIL`) pass. The three defaults in this bullet (interactive exempt, repo layer may not pass secrets, no SSH or GPG agent) await the owner's confirmation.
  - **Accepted residual risk:** the allowlist limits accidental exposure (environment dumps in transcripts and test logs, third-party `acp:` agents). It is not a boundary against a hostile Worker: Workers run as the user with `HOME` set and can read `~/.aws/credentials`, `~/.npmrc` or shell profiles until the sandbox (#53), and Claude Code hands its API key to the commands a Claude Worker runs (its Bash tool): keeping it out needs Claude Code's sandbox, which on Linux also write-protects dependency files and lockfiles, so that choice is with the owner (#150). Adapters built from config (`buildWorkerAdapters`, #149) get `workers.env.pass`; a resolved `agents.*.env` value reaches the agent and is scrubbed from its events and stderr.
  - **Codex and Gemini keep their own key out of the commands a Worker runs** (#150; verified live against the real CLI and a mock API, capability matrix §2, §5). Codex Workers' threads (new and resumed) set `shell_environment_policy.exclude` to the key variables, so their commands get the rest of the Worker environment. Gemini Workers get a home of their own (`GEMINI_CLI_HOME` under the repo's state dir, never the user's `~/.gemini`) whose settings turn on environment redaction and `advanced.ignoreLocalEnv`, and `GEMINI_CLI_TRUST_WORKSPACE` is never passed, so neither the key nor a `.env` (the checkout's or its parents', its `.gemini/.env`, or `~/.env`, which Gemini looks for in that home) reaches them; Gemini sessions from before this change live in the user's `~/.gemini` and cannot be resumed; Gemini's redaction also drops any other secret-looking name, so a secret passed with `workers.env.pass` never reaches a Gemini Worker's commands. Not covered: an `acp:<agent>` other than Gemini, whose commands get what the agent gives them.
- **What a Worker session loads from its checkout** (#181). A checkout is Worker-written: any Worker can commit agent config, hooks or instruction files that a later session there (a retry, a resume, a dependent sub-task) would load, unsandboxed and without Tacet's approval. Each adapter turns that off where the vendor allows it, checked live against a hostile checkout (capability matrix, rows "Project files loaded from the checkout (#181)"):
  - **Claude SDK** (`claude-sdk`; Workers, the planner, the reviewer): `settingSources: []` by default and `strictMcpConfig: true` always, so no user, project or local settings (hooks, permissions, env), no `CLAUDE.md` and no `.mcp.json`. A caller opts in with `sdkOptions.settingSources`, never for a Worker's checkout. Behaviour change: the user's own `~/.claude/settings.json` (e.g. `env` for a Bedrock or Vertex setup) no longer applies to Tacet's Claude sessions; pass those through the environment instead. The PTY preset (`pty:claude`) passes the same `--setting-sources ''` and `--strict-mcp-config`.
  - **Codex** (`codex-app-server`): Codex trusts a repo by itself at the first thread that can write it, which turns on the checkout's `.codex/config.toml` (MCP servers that run commands, instructions, rules) and `AGENTS.md`. For unattended Workers the adapter marks the repo root and the worktree `untrusted` in Tacet's own `CODEX_HOME`, which Codex respects. Interactive sessions use the user's `~/.codex` and trust choices.
  - **claude-agent-acp** (`acp:claude-acp`): Tacet sends `settingSources: []` and `strictMcpConfig` as session options, on `session/new` and also on `session/resume` and `session/fork`, so a resumed or forked Worker keeps them (verified live, #224). Residual: the ACP adapter itself still reads the checkout's `.claude/settings.json` for its permission mode and model list; Tacet pins the session mode, again after a resume or fork, which start in the mode their transcript records (verified on 0.101.0, #224).
  - **Gemini CLI** (`acp:gemini`): the checkout is untrusted (Tacet never passes `GEMINI_CLI_TRUST_WORKSPACE`, and the Worker settings keep folder trust on), so its `.gemini/settings.json`, `GEMINI.md`, skills, agents and `.gemini/.env` do not load. **Open decision:** in an untrusted checkout Gemini also never contacts the MCP server Tacet passes it, so Gemini Workers cannot use `escalate` or the other Mini-conductor tools; trusting the checkout would load everything above (#184).
  - **codex-acp** (`acp:codex-acp`) trusts every session root itself, after any config Tacet can pass, so a checkout's `.codex/config.toml` (an MCP server command ran) and `AGENTS.md` would apply. Nothing on Tacet's side turns that off, so it is **refused for unattended sessions** (see "`acp:codex-acp` is refused for unattended sessions" above; interim default until the owner decides #183).
  - **Not covered:** the managed-settings policy tier (Claude) and an `acp:<agent>` without a built-in spec.
